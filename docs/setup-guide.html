Setup Guide

Every account, key, and setting you need to run the portal, in the order to create them. Two paths: the light demo with one fake author, and production against real HubSpot and Drive data.

1GitHub

The project already has a local git repo. It needs a remote.

1
Decide where it lives: your personal account or an Atmosphere organization. An organization is better if anyone else might ever need access. Creating one is free.
2
Create a private repository named author-portal and push. From the project folder:
gh repo create atmosphere-press/author-portal --private --source=. --remote=origin --push
3
Under Settings → Branches, protect main with "require a pull request before merging" turned off for now. As the only developer you'll push directly, but keep "do not allow force pushes" on.
You now have: a remote for Vercel to deploy from. Every push to main becomes production; every other branch becomes a preview URL.

2Neon (Postgres)

Serverless Postgres. The app talks to it over HTTP, so no connection pooler to run.

1
Sign up at neon.tech. Free tier is fine for the demo and for the first weeks of production. Move to Launch (about $19/month) before inviting real authors, for point-in-time restore.
2
Create a project. Pick the region closest to Vercel's default (US East, Washington). Name it author-portal.
3
In Connection Details, choose Pooled connection and copy the string. It starts with postgresql:// and contains -pooler in the host. This is DATABASE_URL.
4
For production only: create a second branch named preview. Its connection string becomes the Preview-scoped DATABASE_URL in Vercel so pull-request builds never touch production data.

Two databases, two commands. On the demo or preview branch, npm run db:push is fine. On production, always npm run db:generate then npm run db:migrate so every schema change is a reviewed SQL file in the repo.

You now have: DATABASE_URL (and a second one for preview).

3Vercel

Hosting, cron jobs, and the place environment variables live.

1
Sign up with your GitHub account. Hobby (free) is fine for the demo. Production needs Pro ($20/month, one seat) because Hobby forbids commercial use and caps function duration below what the nightly full sync needs.
2
Add New → Project → import author-portal. Framework is detected as Next.js. Don't deploy yet; add environment variables first.
3
Settings → Environment Variables. Paste the values from the master table in section 9. Scope DATABASE_URL separately for Production and Preview.
4
Deploy. The repo's vercel.json registers two crons automatically: incremental sync every 10 minutes and a full reconcile at 03:15 UTC. Confirm both appear under Settings → Cron Jobs.
5
Production only: Settings → Domains → add portal.atmospherepress.com. Vercel shows a CNAME to add at your DNS host. Then set AUTH_URL to https://portal.atmospherepress.com.
You now have: a live URL, working crons, and a place to rotate secrets without redeploying code.

4Resend (email)

Sends magic links, password resets, and invites. Deliverability is the whole login path, so do the DNS properly.

1
Sign up at resend.com. Free tier covers 3,000 emails a month, enough for 1,000 authors. Pro ($20/month) at 20,000 authors.
2
Domains → Add Domain → atmospherepress.com (or a subdomain like mail.atmospherepress.com if you'd rather keep the root domain's DNS untouched). Resend shows DKIM and SPF records. Add them at your DNS host.
3
Add a DMARC record yourself. Resend doesn't prompt for it, but mailbox providers increasingly require it:
_dmarc.atmospherepress.com  TXT  "v=DMARC1; p=quarantine; rua=mailto:quinton@atmospherepress.com"
4
Wait for the domain to show Verified (minutes to a few hours).
5
API Keys → Create → "Sending access" only. This is RESEND_API_KEY. Set EMAIL_FROM to an address on the verified domain, for example Atmosphere Press <portal@atmospherepress.com>.

For the demo you can skip Resend entirely. The seeded accounts have passwords, and Resend's sandbox mode only delivers to your own address anyway.

You now have: RESEND_API_KEY, EMAIL_FROM.

5HubSpot Private App

A token with read scopes plus exactly one write scope, for authors updating their own phone and address.

1
HubSpot → Settings → Integrations → Private Apps → Create a private app. Name it "Author Portal".
2
Scopes tab. Grant these and nothing else:
ScopeUsed for
crm.objects.contacts.readMatching Projects to author emails
crm.objects.custom.readReading Project records
crm.schemas.custom.readDiscovering Project property names from their labels
crm.objects.contacts.writeAuthor self-service phone and address updates only
3
If the phone and address fields turn out to live on the Project rather than the Contact, swap the write scope for crm.objects.custom.write and set contactInfoTarget to project in the portal's app_settings. The code handles both.
4
Create app → copy the access token. This is HUBSPOT_ACCESS_TOKEN. HubSpot shows it once.
5
Find the Project object's type id: Settings → Data Management → Objects → Project. The URL or the object settings shows an id like 2-12345678. This is HUBSPOT_PROJECT_OBJECT_TYPE.

Property names resolve themselves. The portal reads the Project schema and matches your labels ("Pipeline Stage", "DE Assigned", and so on) to internal names automatically. Anything it can't match shows on /admin/health so you can map it by hand.

You now have: HUBSPOT_ACCESS_TOKEN, HUBSPOT_PROJECT_OBJECT_TYPE.

6Google Cloud service account (Drive)

A robot Google account that staff share the author folders with. Read-only by scope.

1
console.cloud.google.com → create a project named atmosphere-author-portal (or reuse one). Enable the Google Drive API under APIs & Services.
2
IAM & Admin → Service Accounts → Create. Name it author-portal-drive. No roles needed; Drive access comes from sharing, not IAM.
3
Open the account → Keys → Add key → JSON. A file downloads. Base64-encode it on one line:
base64 -i ~/Downloads/atmosphere-author-portal-xxxx.json | tr -d '\n'
4
That string is GOOGLE_SERVICE_ACCOUNT_JSON_B64. Delete the downloaded file afterwards; the key is now only in Vercel.
5
In Google Drive, open the top-level folder that contains all author folders → Share → paste the service account's email (the client_email in the JSON, ending in iam.gserviceaccount.com) as Viewer. Copy the folder id from the URL. This is GOOGLE_DRIVE_ROOT_FOLDER_ID and it scopes the admin folder picker.
You now have: GOOGLE_SERVICE_ACCOUNT_JSON_B64, GOOGLE_DRIVE_ROOT_FOLDER_ID.

After deploy, pick provider and model at /admin/assistant, upload the handbook at /admin/handbook, and run the eval before making it active.
You now have: one of the three keys above.

8Two secrets and one email

Generated on your machine, never reused between demo and production.

echo "AUTH_SECRET=$(openssl rand -base64 32)"
echo "CRON_SECRET=$(openssl rand -hex 32)"
  • AUTH_SECRET signs sessions and the admin two-factor cookie.
  • CRON_SECRET is what Vercel Cron presents to the sync endpoint. Vercel reads it from the same env var, so setting it once is enough.
  • ADMIN_BOOTSTRAP_EMAIL is your address. The seed script makes that user the first admin.

10First run

Once the variables are in place.

Demo, locally

cp .env.example .env      # fill DATABASE_URL, AUTH_SECRET, CRON_SECRET, DEMO_MODE=1
npm install
npm run db:push
npm run db:seed -- --demo
npm run dev

Sign in at localhost:3000/sign-in with the password option. Demo logins are in docs/DEMO.md. Push the same branch to Vercel Hobby with the same four variables for a shareable preview.

Production, first deploy

npm run db:generate       # writes the first migration; commit it
npm run db:migrate        # with DATABASE_URL pointing at the Neon main branch
npm run db:seed           # creates your admin from ADMIN_BOOTSTRAP_EMAIL, default stages
  1. Sign in with a magic link. Visiting /admin redirects you to enrol two-factor. Scan the QR with 1Password or Authy.
  2. /admin/health → Run full sync. Watch the sync runs table for ok. Fix any unmapped stage values under /admin/stages and unresolved properties it lists.
  3. /admin/handbook → upload, test a question, make active. /admin/assistant → pick a model.
  4. Invite yourself as an author with a second email address and check the whole flow before inviting anyone else.

The full launch checklist and every runbook live in docs/DEPLOY.md and docs/RUNBOOKS.md in the repo.
